# סטודיו שולחן

חנות עברית למוצרי נייר וכלי כתיבה עם סל קניות שנשמר בין רענונים, סיכום הזמנה, מסך ניהול מוגן ושמירה ב-Supabase.

- ניהול: https://studio-desk-shop.workspace-616380.chatgpt.site/admin.html
- GitHub: https://github.com/adiamar216-colman/studio-shop

## מה עובד

מוצרים נטענים מ-Supabase; חיפוש וסינון לפי קטגוריה; הוספת כמה מוצרים לסל; שינוי כמות והסרת פריטים; מונה פריטים וסכום שמתעדכנים מיד; סיכום הזמנה לפני השליחה ואישור עם מספר הזמנה. נוספו לוגו SVG מקורי וממשק עברי רספונסיבי. סל זמני נשמר במכשיר ל-7 ימים, עם מזהי מוצר וכמויות בלבד וללא פרטי לקוח. מסך הניהול כולל כניסה, פירוט הזמנות, עדכון סטטוס וסינון.

**התוספת למטלה:** סל קניות רב-מוצרים. לקוח שרוצה כמה מוצרים מוסר את פרטיו פעם אחת ומקבל הזמנה אחת. חיפוש וסינון הם תוספת נוספת.

## הפעלה

1. צרו פרויקט Supabase והפעילו את Data API.
2. בהרצה ראשונה בלבד הריצו את `setup.sql` ב-SQL Editor.
3. הריצו את `cart-upgrade.sql`. בפרויקט הקיים מספיק להריץ רק את העדכון, לא שוב את setup.sql.
4. הריצו פעם אחת את `admin-upgrade.sql`.
5. הגדירו ב-`config.js` את Project URL ואת המפתח הציבורי Publishable או anon. אין להכניס Secret key או service_role.
6. הפעילו `python3 -m http.server 8000 --directory dist` ופתחו http://localhost:8000.

## צפייה בהזמנות

פתחו `admin.html` והתחברו עם חשבון מנהלת מורשה. ניתן לצפות בפריטים ולשנות סטטוס בין חדשה, בטיפול והושלמה. רענון הדף דורש כניסה מחדש: אסימוני ההתחברות מוחזקים בזיכרון בלבד.

להקמת מנהלת: ב-Supabase Authentication → Users → Add user יוצרים חשבון עם סיסמה ומוודאים שהוא מאומת. לאחר מכן מריצים ב-SQL Editor את פקודת הרישום ל-`shop_admins` שבסוף `admin-upgrade.sql`, עם כתובת החשבון. חשבון רשום שאינו ברשימה לא מקבל גישה. אין לשמור סיסמאות בקוד או ב-README.

אפשר גם להשתמש ב-Supabase Table Editor:

- `cart_orders`: שורה אחת לכל הזמנה, פרטי הלקוח, הסכום והתאריך.
- `order_items`: המוצרים בהזמנה, מקושרים דרך `order_id` ל-`cart_orders.id`.
- `orders`: הזמנות הבדיקה מהגרסה הישנה; הן נשמרו ללא שינוי.

## החלטות מרכזיות

- HTML, CSS ו-JavaScript ללא תהליך בנייה, כדי לצמצם תלויות ולהגיע למוצר עובד בזמן.
- `products` הוא מקור האמת לקטלוג ולמחירים. הדפדפן שולח מזהי מוצרים וכמויות בלבד; מחיר ושם מוצר נשמרים כצילום מצב בהזמנה.
- המחירים נשמרים כמספרים שלמים באגורות, ללא שגיאות עיגול בחישוב.
- הזמנה נשמרת בפונקציית PostgreSQL אחת ובטרנזקציה אחת: כל הפריטים נשמרים יחד, או שלא נשמר דבר.
- מזהה בקשה ייחודי ונעילה לפי מזהה הבקשה מונעים כפילות בניסיון חוזר מאותו טופס. בקשה עם אותו מזהה ותוכן שונה נדחית.
- RLS והרשאות מפורשות: קריאה ציבורית של מוצרים פעילים בלבד. אין גישה ציבורית לטבלאות ההזמנות. פונקציית SECURITY DEFINER עם search_path ריק מאמתת את הקלט לפני הכתיבה.
- הרשאות מנהלת נבדקות במסד הנתונים לפי Supabase Auth ורשימת `shop_admins`. רק עמודת הסטטוס ניתנת לעדכון; המחיר ופרטי הלקוח אינם ניתנים לשינוי דרך מסך הניהול או ה-API הציבורי.
- סל מקומי נשמר ב-localStorage לפי מזהי מוצרים וכמויות. לאחר רענון המחירים והזמינות נטענים מחדש מהמסד; סל אינו הזמנה עד לשליחה מוצלחת.

## בדיקות

בדיקות הגרסה הראשונה מול מסד אמיתי עברו: טעינת קטלוג, יצירת הזמנה, ניסיון חוזר ללא כפילות, דחיית כמות לא תקינה וחסימת קריאת הזמנות ציבורית.

בגרסת הסל עברו: הוספת מוצרים שונים, עדכון מונה, שינוי כמות, סיכום ושליחת הזמנה דרך הממשק (שלוש יחידות משני מוצרים, 90 ש״ח). מול ה-API נבדקו ניסיונות חוזרים מקבילים ללא כפילות, סל ריק, מוצר כפול, כמות שגויה, שינוי נתונים באותו מזהה בקשה וחסימת קריאת שתי טבלאות ההזמנות לציבור.

בגרסת הניהול נבדקו כניסה עם החשבון המורשה, טעינת הזמנות ופריטים, שינוי סטטוס ושמירתו לאחר רענון. נבדקו גם חסימת מבקרים אנונימיים, אפס הזמנות לחשבון מחובר שאינו מנהל, ומניעת הרשאת עדכון מחיר. שמירת סל לאחר רענון נבדקה בדפדפן.

## מה לא הושלם ומה הייתי מוסיפה בעוד שעה

אין סליקה, משלוחים, שליחת אימיילים או ניהול מלאי. פרטי האימייל מיועדים ליצירת קשר בלבד. אין עדיין הגבלת קצב נגד ספאם. הייתי מוסיפה הגבלת קצב, שחזור סיסמה למנהלת, שמירת חיבור מאובטחת בין רענונים, יומן שינויי סטטוס ובדיקות אינטגרציה אוטומטיות מול מסד בדיקה. שמירת הסל מקומית למכשיר ואינה מסונכרנת בין מכשירים. אין רענון אוטומטי של רשימת ההזמנות; יש כפתור רענון.
